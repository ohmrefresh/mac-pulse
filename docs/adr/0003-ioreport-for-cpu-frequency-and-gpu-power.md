# Read CPU frequency and GPU power through IOReport, matching DVFS tables by shape

The Performance page (`docs/prd/performance.png`) calls for CPU frequency and GPU power, and macOS publishes neither: `hw.cpufrequency*` is Intel-only, and no public API reports GPU watts. Both are available from the private `IOReport` framework, so `IOReportClient` `dlopen`s `/usr/lib/libIOReport.dylib` and subscribes to the CPU complex performance states and the Energy Model — the same source `powermetrics` uses, and possible only because we ship unsandboxed (ADR 0001). This overrides the earlier rule that frequency is a number we simply do not show; it is now measured, and the "never show a value we don't measure" invariant is enforced instead by hiding any row this Mac cannot report.

Neither value can be read directly. IOReport gives residency ticks per DVFS state, not hertz, and the frequency ladders live in the power manager's `voltage-states*` properties, whose names say nothing about which device owns them — every table hangs off a single `pmgr` node. So a ladder is matched to a cluster **by shape**: its entry count must equal the cluster's active state count, it must ascend, and it must stay inside 0.1–7 GHz. That last filter is load-bearing, not defensive: several published tables are not frequency ladders and decode into tens of GHz, and without it a garbage table wins the count match and the rail reads "50.10 GHz". The GPU's ladder has no table of matching length on the machine this was built against, so the GPU clock row simply does not appear, while GPU power — which needs no ladder — does. Energy units are read per channel rather than assumed: on the same Mac, CPU Energy arrives in mJ and GPU Energy in nJ, and assuming one of them made the reading wrong by a factor of a million.

The alternatives were to omit the values (what the code did before, and what the mockup asks us not to do) or to label a cluster's ceiling as a "base frequency" the way the mockup does — rejected because Apple Silicon publishes no base clock, so the number would be a ceiling wearing the wrong name.

The cost is a second fragile surface in the same risk class as ADR 0002, and it is contained the same way: every field is optional, any failure yields nil rather than a crash or a wrong number, and nothing outside the Performance page depends on it — no health, alert, diagnostic or menu-bar value. The subscription is owned by the page's reference-counted visibility gate, so a menu-bar-only session never opens it. If a macOS update renames the channels, the frequency and power rows disappear and the rest of the app is unaffected.
